# 下一目的地预测数据全链路实现方案

## 📊 当前架构分析

### 现有组件
1. **AI模型层 (cidi-model)**: FastAPI服务，包含LSTM预测和分流策略算法
2. **后端层 (cidi-server)**: Spring Boot，提供RESTful API
3. **前端层 (cidi-wx)**: 微信小程序，目前使用前端模拟数据

### 现有数据流
```
AI模型 → Spring Boot → 前端
  ↓
spot_traffic_predictions表 (已实现)
location_hourly_flow表 (已实现)
```

### 问题
- AI模型已经计算出分流推荐数据 (`pairRecommendations`)
- 但这些数据**没有持久化到数据库**
- 前端使用伪随机算法模拟下一目的地预测

---

## 🎯 解决方案：新增 `location_transitions` 表

### 方案概述
利用AI模型现有的 `DiversionPair` 数据（分流推荐），将其持久化为"下一目的地转移概率"数据。

### 数据映射关系
```
AI模型输出 (DiversionPair)          →  数据库表 (location_transitions)
├─ sourceId                        →  sourceLocationId
├─ targetId                        →  targetLocationId  
├─ finalProb                       →  transitionProbability
├─ expectedTransferFlow            →  expectedUsers
└─ predictTime (来自父对象)         →  predictHour
```

## 🗄️ 数据库设计

### 新表：`location_transitions`

```sql
CREATE TABLE location_transitions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    source_location_id BIGINT NOT NULL COMMENT '源景点ID',
    target_location_id BIGINT NOT NULL COMMENT '目标景点ID',
    predict_hour DATETIME NOT NULL COMMENT '预测时间（小时粒度）',
    transition_probability DECIMAL(6,4) NOT NULL COMMENT '转移概率 (0-1)',
    expected_users INT NOT NULL COMMENT '预期转移人数',
    coupon_amount DECIMAL(6,2) DEFAULT 0 COMMENT '推荐优惠券金额',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    
    INDEX idx_source_predict (source_location_id, predict_hour),
    INDEX idx_predict_time (predict_hour),
    
    CONSTRAINT fk_source_location FOREIGN KEY (source_location_id) 
        REFERENCES locations(id) ON DELETE CASCADE,
    CONSTRAINT fk_target_location FOREIGN KEY (target_location_id) 
        REFERENCES locations(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='景点间人流转移预测';
```

## 🔍 关键技术点

### 数据聚合逻辑
由于AI模型每次预测只生成"下一小时"的转移数据，前端需要"未来6小时"的数据，有两种方案：

**方案A（推荐）**: 前端聚合
- 后端只返回最新一轮预测的转移数据
- 前端根据当前时间推算未来6小时的时间点
- 优点：简单，数据准确

**方案B**: 后端聚合
- 后端查询最近6轮预测结果
- 按时间排序返回
- 优点：前端逻辑简单

### Service层实现示例（方案A）
```java
public List<NextDestinationDTO> getNextDestinations(Long sourceLocationId, int hours) {
    // 获取最新一轮预测
    List<LocationTransition> transitions = repository.findLatestBySourceLocation(sourceLocationId);
    
    if (transitions.isEmpty()) {
        return Collections.emptyList();
    }
    
    LocalDateTime baseTime = transitions.get(0).getPredictHour();
    List<NextDestinationDTO> result = new ArrayList<>();
    
    // 生成未来N小时的预测（基于同一轮数据）
    for (int i = 0; i < hours; i++) {
        LocalDateTime targetHour = baseTime.plusHours(i);
        NextDestinationDTO dto = new NextDestinationDTO();
        dto.setHour(targetHour.format(DateTimeFormatter.ofPattern("HH:mm")));
        
        // 取Top3转移目标
        List<TransitionItem> items = transitions.stream()
            .limit(3)
            .map(t -> {
                TransitionItem item = new TransitionItem();
                item.setLocationId(t.getTargetLocationId());
                item.setLocationName(getLocationName(t.getTargetLocationId()));
                item.setRatio(t.getTransitionProbability().doubleValue());
                item.setRatioText(Math.round(t.getTransitionProbability().doubleValue() * 100) + "%");
                item.setUsers(t.getExpectedUsers());
                return item;
            })
            .collect(Collectors.toList());
        
        dto.setTransitions(items);
        result.add(dto);
    }
    
    return result;
}
```

## 📝 总结

这个方案充分利用了现有架构和AI模型的计算结果，只需：
1. 新增1张数据库表
2. 新增1个Spring Boot模块（约5个文件）
3. 修改FastAPI的1个函数（添加写入逻辑）
4. 修改前端的1个函数（替换API调用）

**无需重新训练模型，无需修改核心算法**，即可实现从模型到前端的完整数据链路。
