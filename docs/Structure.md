# Structure

## 项目定位

本项目是一个面向旅游场景的多景区游客协调分流系统，目标是结合景区数据采集、拥挤度量化、客流预测和路线推荐能力，为游客提供出行建议，并为管理端提供监测与预警支持。

从当前仓库状态看，这个项目并不是单一后端 + 单一前端的简单结构，而是一个处于持续演进中的多模块工程。它同时包含：

- 微信小程序前端
- 微信云函数后端
- Python Flask 模拟/算法服务
- Java Spring Boot 主业务后端
- Node.js 临时 Mock 服务
- 文档、数据库脚本与项目规范

因此，这个仓库既包含“当前可演示的实现”，也包含“未来正式化落地的后端骨架”。

## 总体架构理解

这个仓库可以分为五层来理解。

### 1. 表现层

主要是微信小程序，负责用户交互、地图展示、文章动态、收藏、搜索、个人中心等页面能力。

对应目录：

- `devs/frontend/cidi-wx`

### 2. 接口与服务层

当前存在三套服务实现，职责并不完全相同：

- 微信云函数：承担当前小程序演示阶段的主要后端能力
- Python Flask：承担景区搜索、详情抓取，以及后续算法接口承载
- Java Spring Boot：作为正式业务后端的主框架，当前已搭好基础结构但业务实现仍较少

### 3. 数据与算法层

该层包含两类内容：

- 一类是景区数据抓取、Mock 数据、云数据库数据
- 一类是拥挤度计算、客流预测、协同分流等建模/算法能力

### 4. 文档与治理层

`docs` 中沉淀了需求、数据库设计、接口说明、模型说明、测试报告等内容；`standard.md` 约束了代码规范、提交规范和项目协作方式。

### 5. 脚本与辅助层

`devs/script` 中放置数据库建表 SQL 和开发辅助脚本，承担初始化和团队协作支持作用。

## 各模块详细说明

## 一、前端模块：微信小程序

目录：`devs/frontend/cidi-wx`

这是当前项目中最完整、最接近真实产品形态的部分，负责面向游客用户提供主要交互界面。

### 页面结构

主包页面：

- 首页 `pages/index`
- 动态 `pages/updates`
- 地图 `pages/map`
- 收藏 `pages/collections`
- 个人中心 `pages/profile`
- 搜索 `pages/search`

分包页面：

- 文章详情 `pages_sub/article`
- 地点详情 `pages_sub/location`
- 设置 `pages_sub/settings`
- 反馈 `pages_sub/feedback`
- 登录 `pages_sub/login`
- 发布 `pages_sub/publish`

### 前端职责

- 展示景区与文章内容
- 展示地图标记点与地点详情
- 提供内容发布、评论、点赞、收藏等互动能力
- 提供搜索和预测结果展示入口

### 当前数据来源

小程序当前并不是直接全面依赖 Java 主后端，而是优先通过微信云函数获取数据。

主要调用方式：

- 首页、互动、搜索等功能通过 `cidi-api` 云函数完成
- 地图数据通过 `getMockData` 云函数返回
- 预测能力通过 `getPrediction` 云函数返回 Mock 结果

此外，前端还保留了未来对接 Spring Boot 的接口开关，这说明项目设计上有从“云函数演示版本”向“正式服务端版本”迁移的意图。

---

## 二、微信云函数模块

目录：`devs/frontend/cidi-wx/cloudfunctions`

云函数是当前小程序后端能力的核心承载层，相当于项目现阶段最实际可用的一层服务端。

### 1. cidi-api

这是一个统一 action 分发的业务云函数，承担了大量小程序后端逻辑，包括：

- 发布帖子
- 获取首页文章列表
- 获取用户收藏列表
- 获取文章详情
- 点赞/收藏切换
- 评论新增与列表获取
- 搜索文章内容

这部分逻辑已经具备较明显的“内容社区”产品特征，不只是景区查询，还包含用户内容互动。

### 2. getMockData

该云函数直接返回静态 Mock 数据，主要服务于：

- 首页展示
- 地图地点标记
- 动态流
- 收藏页
- 地点详情页
- 文章详情页

它的作用是让前端在正式后端未完成之前也能独立联调和演示。

### 3. getPrediction

该云函数当前返回的是模拟预测结果，包含：

- 景点未来时段拥堵等级
- 趋势说明
- 预测人数
- 文字化建议

它代表的是“预测能力的产品接口形态”，虽然目前内部逻辑仍是 Mock。

### 4. login

该云函数用于获取用户 OpenID，并返回简化的用户信息，支撑小程序登录态和展示逻辑。

## 三、Python 模拟/算法服务

目录：`devs/backend/cidi-mock`

这是一个 Flask 项目，是当前仓库中最接近“算法接口服务”的后端模块。

### 模块结构

- `run.py`：项目启动入口
- `app/api`：接口定义层
- `app/spider`：景区爬虫逻辑
- `app/algorithm`：算法目录
- `app/utils`：配置与响应工具
- `app/static/templates`：接口文档静态页面

### 当前职责

根据已有代码和 README，这个模块主要承担两类任务：

1. 景区数据抓取接口
2. 算法能力接口承载

### 当前接口形态

现有蓝图统一挂载在 `/api/v1` 前缀下，已实现的核心接口包括：

- `/search`：按关键词搜索景区
- `/spot/detail`：查询景区详情
- `/doc`：查看接口文档页面

### 在整体架构中的定位

这个模块更偏“数据侧 + 算法侧”服务，而不是完整业务中台。它适合承载以下能力：

- 外部旅游平台数据抓取
- 拥挤度计算
- 客流预测
- 为前端或 Java 服务提供算法结果

因此，它是项目中“模型算法端”的现实落地点。

## 四、Python 建模目录

目录：`devs/backend/cidi-model`

该目录目前主要是预留性质，README 中强调先搭框架、再逐步沉淀建模代码，并且预期会多次重构。

它说明项目在架构上区分了两种 Python 能力：

- `cidi-mock`：偏接口与可运行服务
- `cidi-model`：偏纯算法与建模实验空间

这是一种合理的拆分方式，因为建模代码通常迭代快、实验性强，而接口服务需要稳定性更高。

## 六、Node.js 临时 Mock 服务

目录：`devs/backend/nodejs临时返回数据`

这是一个基于 Express 的临时服务，用于在项目早期为前端快速提供固定返回值。

### 它的作用

- 提供登录接口
- 提供首页、动态、地图、地点详情、文章详情、收藏等接口
- 让前端在没有正式后端时可以独立开发

### 它的定位

这个模块并不是最终架构中的正式核心，而是一个典型的“过渡型支撑模块”。

仓库中的 README 也明确建议，后续更适合将这类能力迁移到 Python 或正式后端中，因为模拟数据、定时任务和数据库操作会越来越复杂。

## 当前真实运行链路

从仓库现状来看，项目当前更接近下面这条运行链路：

```text
微信小程序
   ├─ 调用微信云函数 cidi-api 处理社区/内容类业务
   ├─ 调用微信云函数 getMockData 获取演示用地点和文章数据
   ├─ 调用微信云函数 getPrediction 获取模拟预测结果
   └─ 预留未来直连 Spring Boot 的接口能力

Python Flask
   ├─ 提供景区搜索与详情接口
   ├─ 调用 spider 抓取外部旅游平台数据
   └─ 预留算法接口承载能力

Java Spring Boot
   ├─ 已完成正式后端骨架搭建
   ├─ 已接入数据库/JWT/配置体系
   └─ 未来承接核心业务服务
```

也就是说，当前项目不是“所有能力都已经统一接到 Java 主后端”，而是一个多条链路并存的阶段性架构。

## 架构演进关系

如果从工程演进视角看，这个项目大致经历或正在经历以下过程：

1. 先用 Node.js 临时接口支撑前端开发
2. 再用微信云函数快速形成可演示版本
3. 同步使用 Python 构建爬虫和算法接口
4. 最终将正式业务收拢到 Spring Boot 主服务

这种演进路径很符合学生项目或早期原型项目的实际节奏：

- 先保证能展示
- 再补真实数据
- 再沉淀正式后端
- 最后统一业务架构
