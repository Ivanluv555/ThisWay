## 04 数据设计

> 基线：2026-11-06。以下物理字段从仓库 SQL 提取，不代表实际数据库 schema 已探测；Java 映射另列，二者差异必须显式处理。

### 4.1 数据域与访问边界

| 数据域 | 表 |
| --- | --- |
| 用户与权限 | `users/admin/user_settings/user_follows` |
| 景点与资源 | `locations/location_images/categories` |
| 社区与反馈 | `posts/post_images/comments/actions/feedbacks/feedback_images` |
| 搜索 | `hot_searches/search_history` |
| 客流与模型结果 | `location_hourly_flow/spot_traffic_predictions/location_transitions` |
| 独立采集 | `spider_regional_scenic_spots/spider_scenic_spot_details` |
| 待确认旧表 | `locations_predictions`，没有当前对应 Java 实体 |

业务数据经 Java/JPA 访问；FastAPI 通过 HTTP 读写，爬虫同步仍直连 `spider_*`。当前 Java 默认库名 `cidi-db`、采集默认 `cidi_db`，部署时显式选择。人数、概率、拥挤指数和时间口径见 [05 模型](./05-模型与预测.md)。

### 4.2 建库、初始化与种子

1. 创建隔离数据库和专用账号；基础 schema 为 [cidi_db.sql](../script/sql/cidi_db.sql) 中的 16 张业务表。它含 `DROP TABLE`，只用于选定空库/可丢弃环境的重建，不作为增量迁移。
2. 导入 `location_hourly_flow.sql`、`location_transitions.sql`，它们引用 `locations`，用于预测链路。
3. 启用采集时导入两个 `spider_*` SQL；均含重建动作。`locations_predictions.sql` 是独立旧表，只有明确使用其种子/功能时才导入。
4. 确保基础用户/分类/景点数据后再导入依赖其 ID 的种子；`seed_5_rows_per_table.sql`、`seed_location_transitions.sql`、`seed_locations_predictions.sql` 是独立示例，不能盲目连续导入。最后一份写的是旧 `locations_predictions`，不会填充当前预测 API 使用的表。
5. 验证必需表、外键、唯一约束与实体映射；保存执行顺序和结果。当前没有统一增量迁移系统。

[21 景点示例](./13-示例数据/01-重庆景点.json) 只含 ID、名称、坐标，不能直接替代完整 `locations` 记录，也不保证与所有测试固定 ID 一致。

### 4.5 尚未统一的 schema 规则

- 主 dump 中部分列与 Java 的默认值、精度/长度不完全一致，JPA `ddl-auto=update` 也可能改变运行库；应在隔离库实际比对后制定迁移，不能用一份字典自动宣布一致。
- `location_hourly_flow` 有 `(location_id,record_hour)` 唯一约束；转移表有查询索引，但无同轮源/目标唯一键，`saveAll` 本身不代表幂等。预测批量写入同样需评估重复执行。
- `locations_predictions` 与 `spot_traffic_predictions` 字段和引用名不同，当前客户端/Java API 采用后者；不要将旧表种子当作当前接口数据。
- 景区区域设计曾有 `spot_regions` 与后来简化的三表草案，当前 SQL/实体中未落齐，应使用下面统一草案继续设计，不将其列为已存在表。
