
### 代码规范

- 后端 Java 开发代码规范参考《阿里巴巴开发手册》
- 文件行数限制：单份代码文件代码量不超过 1200 行，避免耦合度过高
- TODO 标记：使用 TODO: xxxx 对代码进行标记，便于编辑器快速定位待办事项
- 禁止魔法变量：代码中不允许出现无名字、无解释、凭空出现的硬编码值（魔法变量）。任意魔法变量都应使用常量 / 枚举 + 有意义的命名替代。
> 魔法变量举例：
> - a = b + c + "666"，这里的 “666”
> - if (age > 18) 这里的 “18” 也是魔法变量


### Git 规范

> Git 使用规范化虽看似繁琐费时，但对项目管理至关重要，需养成良好习惯
> 别人提交的代码需要 review 

- Commit 格式：
  
```plaintext
type(scope): message
// 这里是空行
[body] 
// body 可选，详细说明改动原因、思路、实现方式，每行不超过 72 字符
```

```plaintext
<!-- 示例： -->
feat(search): 新增搜索功能

- 支持景区精准/模糊匹配
- 支持拼音全拼/简拼匹配
- 支持城市名称匹配
```

- 提交原则：

  - 提交内容需分类，避免同时提交多个不同类型的内容。建议 “一件事一件事做”，减少使用 “git add .” 的次数。
  - 先只 commit，不要频繁 push，积累多个 commit 后再统一 push，并合并内容量少的 commit。
  - 不要一次性提交大量内容，每次开始工作前，可以把上次写的代码提交一次。

- 提交类型分类：

  - docs：仅文档修改（如 README、代码注释、.gitignore 等）
  - refactor：在不影响代码逻辑与正常功能的前提下，进行代码重构、统一代码风格等
  - fix：修复 Bug 
  - feat：新增功能
  - test：测试代码

- 分支管理：
  
  - 核心流程（小型团队）
    1. 从 `master` 切出 `feature/somebody/data-visualization` 开发数据可视化功能；
    2. 开发过程中定期提交，完成后提交 Pull Request（PR）；
    3. 团队 Code Review 通过后，合并到 `master`；
    4. 合并后立即部署到生产环境。
  - 分支命名规范：`feature/开发者/功能描述`，（如：`feature/zhangsan/data-visualization`）

- 实操示例（链接里有完整的实操过程，刚开始不熟悉慢慢来，可以用临时仓库测试效果）：https://www.doubao.com/thread/w3cc1e6449d70a120
- 在线 Git 可视化学习网站（仓库沙盒环境）：https://learngitbranching.js.org/?locale=zh_CN


### 项目管理规范

> 通过规范化的项目管理，提升团队协作效率与项目可维护性

- Markdown 格式规范：

  - 标题等级：文档标题为 2 级标题（##），子标题从 3 级标题（###）开始依次递进，避免标题等级过高导致字体过大。
    - 示例：## 文档标题 → ### 子标题 → #### 子子标题
  - 内容分割：若内容板块不同，建议用 --- 分割线区分，提升可读性（可参考仓库根目录的 README）。
  - 注释格式：使用 > 作为注释，对内容进行补充说明，一般放在标题下方或对应内容下方。
  - 显示图片需使用稳定的在线链接，同时注意控制图片大小，避免因占用内存过大导致 GitHub/Gitee 无法加载。

- README.md 要求：

  - 完整文件夹需配套 README.md，用于概括目录结构、业务逻辑、交互关系与必要备注说明，便于快速理解项目。
  - 建议先对全局框架结构建立清晰认知，再针对具体内容看细节；可生成文件树并说明文件用途。

- 项目协作规范：

  - 启动项目前，建议先咨询 AI，了解实现功能的经验、工具、技术栈等。
  - 若有相关内容的修改、调整，需在群里通知并说明修改细节，及时同步团队。

- 文件命名规范：

  - 无关联的文件可按重要性 | 使用频率等进行顺序编号，固定文件相对位置，形成肌肉记忆，方便快速定位（可参考 docs 文件夹）。
